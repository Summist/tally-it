# AGENTS.md — TallyIt

Требования и правила проекта. Читать целиком перед любой работой в репозитории. Если код противоречит этому файлу — прав файл, а не код.

## 1. Что это

TallyIt — личное веб-приложение для учёта КБЖУ с поправкой на то, что сырой вес не равен готовому.

Проблема: в обычных дневниках питания рецепт считается по сырым ингредиентам, а после готовки масса меняется (выпаривание, ужарка). Приходится вручную считать пропорцию в калькуляторе и пересчитывать порцию.

Решение: ингредиенты вносятся сырыми, потом фиксируется вес готового блюда, и КБЖУ пересчитывается на 100 г готового продукта. Дальше съеденное записывается граммами и попадает в дневник и в отчёт тренеру.

## 2. Пользователь и основной сценарий

Один пользователь — владелец. Без команд, без ролей, без второго аккаунта.

Основной сценарий: сварил блюдо → внёс ингредиенты с сырыми весами → взвесил готовое → увидел КБЖУ на 100 г → записал съеденное в приём пищи с фото → получил текст отчёта для тренера.

## 3. Домен и формула

```
КБЖУ блюда на 100 г = сумма КБЖУ всех ингредиентов / вес готового блюда × 100
```

Сущности:

| Понятие | Смысл | Изменяемость |
| --- | --- | --- |
| **Product** | товар из справочника: название, бренд, магазин, вес упаковки, КБЖУ на 100 г, источник и дата источника | правится и архивируется |
| **Dish** | блюдо: набор ингредиентов и вес готового | правится и удаляется свободно |
| **Ingredient** | строка блюда: `productId` + **снимок** названия и КБЖУ на 100 г + сырой вес | правится вместе с блюдом |
| **Meal** | приём пищи: дата, время, тип, фото, заметка | правится |
| **MealEntry** | строка приёма: **снимок** названия и КБЖУ + граммы | неизменяемый снимок |
| **Goal** | цель КБЖУ (ккал, Б/Ж/У) | меняется, история не нужна (v3) |

Правило снимков: любая связь через границу хранит копию значений. Правка или удаление продукта не меняет блюдо; правка или удаление блюда не меняет приёмы пищи. История не переписывается никогда.

## 4. Контексты и границы

Шесть контекстов, каждый — модуль с собственной схемой в Postgres.

| Контекст | Владеет | Знает про других |
| --- | --- | --- |
| **Identity** | пароль, хеш, сессии, `userId` | ничего |
| **Profile** | цель КБЖУ, параметры тела | только `userId` |
| **Catalog** | продукты, источники данных, происхождение КБЖУ | только `userId` |
| **Kitchen** | блюда, ингредиенты, вес готового, пересчёт | `userId`, `Catalog.Contracts` для поиска продукта |
| **Diary** | приёмы пищи, снимки позиций, фото, итоги | `userId`, `Kitchen.Contracts`, `Profile.Contracts` |
| **Export** | сборка отчёта | `userId`, `Diary.Contracts` |

Правила границ:

1. Модуль ссылается только на `TallyIt.BuildingBlocks` и на **свой** `*.Contracts`.
2. Снаружи модуль доступен только через `*.Contracts`.
3. Между схемами нет внешних ключей. Только идентификаторы.
4. Identity не имеет `Contracts`: остальные получают `userId` из токена и никогда не обращаются к Identity.
5. Проценты от нормы считает Diary по **текущей** цели Profile. Сами КБЖУ приёмов не пересчитываются.

## 5. Стек

| Слой | Выбор |
| --- | --- |
| Backend | .NET 10 LTS, ASP.NET Core Minimal API, EF Core |
| База | PostgreSQL, отдельная схема на модуль |
| Кэш | Redis, только кэш чтения; потеря кэша не влияет на корректность |
| Поиск | Elasticsearch, вторичный индекс, наполняется через outbox |
| Frontend | Next.js (App Router), TypeScript, мобильный первым |
| Инфраструктура | Docker Compose: postgres, redis, elasticsearch |
| Хостинг | домашний ПК, доступ с телефона по локальной сети, позже VPS |

Всё, что хранит данные и образы, живёт на диске `D:`.

## 7. Правила модульного монолита

1. Один проект на модуль плюс `*.Contracts`, где нужен внешний интерфейс. Дробление на Domain/Application/Infrastructure не делать.
2. `DbContext` — ровно один на модуль, миграции — на модуль.
3. В `*.Contracts` только DTO, события и интерфейсы. Никаких EF-типов, доменных сущностей и generic-репозиториев.
4. Межмодульное общение: синхронный вызов через интерфейс из `*.Contracts` либо событие через `shared.outbox`. Прямой SQL через границу запрещён.
5. Api — только композиция: регистрация модулей, middleware, маппинг HTTP в команды. Бизнес-логики в Api нет.
6. Воркеры — отдельные процессы, не фоновые задачи внутри Api.
7. Никакого MediatR, AutoMapper и прочей инфраструктурной магии: команда — обычный класс с методом `Execute`.

## 8. Данные и КБЖУ

1. КБЖУ считаются в `decimal`, никогда в `double`.
2. Округление только на выводе: калории целыми, граммы и БЖУ — один знак после запятой. В расчётах округления нет.
3. Единицы ввода — граммы. Упаковки, штуки, ложки и доли блюда не поддерживаются.
4. У каждого значения КБЖУ хранится источник (`manual`, `magnit`, `lenta`, `x5`, `openfoodfacts`) и дата получения.
5. Остатков блюда, веса тары и сроков годности нет — эти сущности сняты сознательно.
6. Фото лежат файлами в `data/photos/`, в базе только путь. Сжатие до 1600 px по длинной стороне, EXIF вырезается, до 5 фото на приём.

## 9. Тесты

Четыре вида, четыре проекта.

| Вид | Что проверяет | Инструменты |
| --- | --- | --- |
| Unit | пересчёт КБЖУ, суммы приёма, округление, границы (0 г, пустое блюдо, отрицательный вес) | xUnit + Shouldly, без БД |
| Integration | Postgres в контейнере, миграции, эндпоинты, outbox → индексатор, кэш и его инвалидация | WebApplicationFactory + Testcontainers + Respawn |
| Architecture | правила границ из разделов 4 и 7 | NetArchTest |
| E2E | готовка и отчёт целиком в браузере, десктоп и мобильный viewport | Playwright |

Минимальные архитектурные тесты:

1. `TallyIt.Modules.X` не ссылается ни на один `TallyIt.Modules.Y`, где `Y != X`.
2. Никто, кроме модуля, не ссылается на `TallyIt.Modules.X` напрямую — только на `.Contracts`.
3. В `*.Contracts` нет типов из `Microsoft.EntityFrameworkCore`.
4. Каждый модуль реализует `IModule` и регистрируется без ручного перечисления.
5. Ни один тип из `TallyIt.Identity` не виден за пределами `TallyIt.Api`.

E2E-дымовой набор: (1) продукт → блюдо → вес готового → КБЖУ на 100 г; (2) приём с фото и итог; (3) отчёт дня. Парсинг в E2E не участвует — он покрывается интеграционным тестом на сохранённом HTML-снимке карточки.

## 10. Объём работ

MVP — без голоса, без парсинга, ручной ввод.

| Контекст | MVP | v2 | v3 |
| --- | --- | --- | --- |
| Identity | вход по паролю, выход | смена пароля, «запомнить устройство» | — |
| Profile | задать и смотреть цель КБЖУ | параметры тела, расчёт нормы, история цели | динамика веса |
| Catalog | добавить вручную, найти свой продукт, развесной товар | добавить по ссылке (Магнит), поиск в каталоге Ленты, Пятёрочка через браузер, правка с историей, обновление из источника | штрихкод камерой, фото этикетки |
| Kitchen | создать блюдо, добавить и поправить ингредиент, зафиксировать вес готового, увидеть КБЖУ | шаблон блюда, приготовить заново, масштабировать, блюдо как ингредиент, показ потери веса | — |
| Diary | приём пищи, блюдо и продукт граммами, фото, итог приёма и дня | цель и проценты, неделя и графики, правка приёма | — |
| Export | отчёт дня текстом, копирование в буфер | фото вложениями, отправка с телефона одним действием, коллаж дня, отчёт за неделю | — |
| Платформа | доступ с телефона по сети, бэкап базы | PWA, переезд на VPS | — |
| Ввод | — | — | push-to-talk, wake word, разбор фразы, отмена записи |

Полные сценарии — в диаграммах, см. раздел 17. Идентификаторы `UC-*` — общие для кода, тестов и обсуждений.

## 11. Парсинг каталогов сетей

1. Кэш и своя база первыми: внешний источник вызывается только при промахе.
2. Контракт источника: `search(query)` и `fetchProduct(url)`. Реализации — по адаптеру на сеть, ядро Catalog о сетях не знает.
3. Магнит: обычный HTTP, карточка серверная, КБЖУ в HTML, поиск на сайте клиентский — только по ссылке.
4. Лента: официальный JSON API без авторизации, поиск есть, КБЖУ нет.
5. Пятёрочка и Перекрёсток: HTTP блокируется ServicePipe (JS-челлендж), доступ только через реальный браузер с живым профилем.
6. Уважать чужие правила: robots.txt, ограничение частоты, никаких массовых обходов. Только свои покупки.
7. Тесты парсеров — на сохранённых HTML-снимках, не на живых сайтах.

## 12. Интерфейс

1. Мобильный первым: кухня, руки заняты, телефон на столе.
2. Один вход по паролю, сессия в подписанной cookie, HTTPS не обязателен в локальной сети, но пароль обязателен всегда.
3. Главный экран готовки: текущее блюдо, сумма КБЖУ, поле веса готового, крупные кнопки.
4. Числа не врут: показывать источник КБЖУ и дату, если он из каталога.
5. Язык интерфейса — русский, валюта — рубль, даты — локальные.
6. Отчёт для тренера — короткий текст: дата, приём, позиции, итог. Не PDF.

## 13. Нефункциональные требования

1. Запуск с нуля: `docker compose up -d` плюс два процесса (`dotnet run`, `npm run dev`).
2. Основные операции — мгновенные на локальной сети, без ожидания внешних сервисов.
3. Падение Redis, Elasticsearch или воркера не ломает учёт: они вторичны.
4. Бэкап базы — одна команда, файл на `D:`.
5. Персональные данные не уходят наружу. Никакой телеметрии.
6. Логи — структурированные, без содержимого приёмов пищи и паролей.

## 14. Запрещено

1. Считать КБЖУ в `double` или округлять на промежуточных шагах.
2. Хранить в приёме пищи ссылку на блюдо вместо снимка значений.
3. Делать общие таблицы между модулями и джойнить через границу контекста.
4. Вводить остатки блюда, вес тары, сроки годности — снято сознательно.
5. Тащить MediatR, AutoMapper, generic-репозитории, «слои ради слоёв».
6. Писать в Api бизнес-логику.
7. Ходить в чужие каталоги на каждый запрос пользователя.
8. Коммитить `data/`, фото, `.env`, пароли.

## 15. Процесс работы

1. Задачу ставит владелец. Агент пишет код, владелец ревьюит и принимает результат.
2. Агент не коммитит и не пушит без прямой просьбы.
3. Одна задача — один связный дифф. Рефакторинг не смешивается с фичей.
4. Перед сдачей: сборка, все четыре вида тестов, ручная проверка сценария.
5. Новое архитектурное решение фиксируется строкой в этом файле, а не только в коде.
6. Спорное решение выносится владельцу с рекомендацией, а не решается молча.

## 16. Definition of Done

1. Фича покрыта unit-тестами на логику и integration-тестом на сценарий с базой.
2. Архитектурные тесты проходят, границы не нарушены.
3. E2E-сценарий не сломан.
4. Миграции созданы и применяются с нуля.
5. Ни одно правило из разделов 4, 7, 8, 14 не нарушено.
6. Диаграммы обновлены, если изменились границы или сценарии.
